### 1.2 后端机制（`backend/campus-common`）

包 `cn.iocoder.yudao.module.campus.common.api`：

- `CampusResponse`：`code/message/data/traceId` 信封，成功与失败都带 traceId。
- `CampusErrorSpec`、`CampusErrorCodes`、`CampusRetryAction`、`CampusErrorDetail`、`CampusFieldError`：错误规范与恢复信息。
- `CampusApiException`：领域异常，由统一处理器映射。
- `CampusExceptionHandler`：按包限定（`cn.iocoder.yudao.module.campus`）的异常映射，最高优先级。
- `CampusUnmappedPathExceptionHandler`：未匹配地址的 404 契约响应；非校园前缀重新抛出，保持上游行为。
- `CampusTraceContext`、`CampusTraceFilter`：仅校园路径/readiness 的服务端 traceId、MDC 与响应头回显；不信任客户端自带 `X-Trace-Id`。
- `CampusPageParam`、`CampusPageResult`、`CampusApiContract`：分页与契约常量。
- `api.security/*`：装饰芋道 401／403 处理器；校园路径输出真实 HTTP 状态与校园信封，非校园路径委托原实现。

包 `...common.api.json`：

- `MoneyFen`（整数分，拒绝小数与字符串）、`CampusIdString`（公开 DTO 使用 String，拒绝数字 token）、`CampusTimestamp`（RFC 3339 带偏移）。

包 `...common.event`：`CampusEventEnvelope`、`CampusEventEnvelopeValidator`、`CampusEventVersionPolicy`、`CampusEventVersionStatus`。

`health/CampusReadinessController` 改为返回校园信封（`message` + `traceId`），业务数据仍只有 `{"status":"UP|DOWN"}`。

## 2. 契约冻结内容

1. **入口**：`/app-api/campus/v1`（学生端）、`/admin-api/campus/v1`（管理端）、`/health/readiness`（运维探针）。上游 `system`／`infra` 入口保持 yudao 原有信封。
2. **信封**：`code`、`message`、`data`、`traceId`；错误时 `data` 为 `CampusErrorDetail`（`retryable`、`requiredAction`、`fieldErrors`、`currentVersion`、`currentState`）。
3. **错误码区间**：校园自有业务码 `1_040_000_xxx`（`1` = 业务级，`040` = 校园系统段，第三段为子模块段，第四段为序号）；HTTP 语义码直接复用上游 400／401／403／404／429／500。
4. **HTTP 映射**：400 参数／金额／分页／事件信封；401 未认证；403 无权限；404 不存在或不可见；409 版本／幂等冲突、命令处理中、事务重试耗尽；429 限流；501 事件版本不支持；500 兜底脱敏。
5. **类型规则**：公开 DTO 的 ID 为 String 且数字 token 返回 400；金额为整数分（`MoneyFen`，小数与字符串 400）；时间为带偏移 RFC 3339（`@CampusTimestamp`，epoch 与无偏移时间 400）。
6. **分页**：默认 `pageNo=1`、`pageSize=20`，硬上限 100；导出等全量场景必须走独立接口与授权。
7. **事件**：信封字段固定，载荷禁止证件与取件码（键名归一化后匹配即拒绝）；未知类型／版本必须可观察失败。
8. **契约一致性**：错误码文档与代码由用例强制对齐；契约自检额外校验 `$ref`、operationId、Example Object、路径前缀和事件规则；Redocly 做标准语义 lint。

## 5. 架构决策（请架构负责人复核）

1. **校园入口使用独立信封 `CampusResponse`**：上游 `CommonResult` 为 `code/msg/data`，被 system／infra 入口与既有前端依赖；M00.02 要求校园入口固定 `code/message/data/traceId`，因此新增信封而不改写上游。代价是同一应用内存在两种信封，边界按入口前缀划分并写入 `contracts/README.md`。
2. **错误码区间 `1_040_000_xxx`**：上游已占用 `1_001`–`1_022`（含注释中的预留段），校园取 `040`，并把第三段（模块位）留给 M01–M11 逐模块分配。
3. **`/health/readiness` 信封随之变更**：M00.01 文档中 `{"code":0,"msg":"","data":{"status":"UP"}}` 的示例与 `Tests run: 20` 的计数都属该次验收的历史证据；现行响应为 `message` + `traceId`。数据语义与就绪判定未变。
4. **未匹配地址处理单独成类**：按包限定的 advice 在没有匹配控制器时不会生效，因此 404 处理器不限包，改由 URL 前缀判定；非校园前缀重新抛出，交回上游链路。
5. **时间格式显式化**：上游 `application.yaml` 打开了 `spring.jackson.serialization.write-dates-as-timestamps`，实测未标注的 `OffsetDateTime` 会输出 epoch 数字（如 `1789611330.000000000`），因此校园 DTO 的时间字段必须标注 `@CampusTimestamp`。
6. **安全处理器采用委托装饰**：不改芋道源码，通过 BeanPostProcessor 包装固定上游 Bean；只在精确校园前缀/readiness 改写，其他路径调用原处理器。
7. **trace 信任边界**：客户端 `X-Trace-Id` 不作为可信身份；可信网关使用标准 trace context 建立 OpenTelemetry 活动链路，否则服务端生成编号。过滤器不再作用于非校园路径。

## 6. 变更与边界

- 新增文件全部位于 `contracts/`、`backend/campus-common/src/{main,test}` 与 `backend/docs/`；上游 Java 源码保持零改动（仅 `campus-common` 内已有的就绪控制器返回类型改为校园信封）。

- 删除字段、改变错误码数值或调整分页上限属于破坏性变更，必须先提升 `CampusApiContract.VERSION`。
