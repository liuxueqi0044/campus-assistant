# 校园助手：开源复用选型清单

核查日期：2026-09-17。范围：官方仓库、许可证、文档、部分源码与依赖文件。尚未完成整套源码编译、真机联调、安全审计或生产压测。

## 1. 复用决策

采用组合式复用：学生端模板＋基础组件、配套管理端＋后端框架、文件解析／OCR、微信支付 SDK。校园业务由我们独立维护。没有选定一个现成的“校园全功能项目”直接上线，原因是目前核查的候选还不能同时证明其授权、业务闭环、维护能力和架构适配满足要求。

具体判断顺序：业务适配程度 → 许可证与依赖授权 → 能否构建和测试 → 维护状态 → 改造与升级成本。星标数、演示视频、README 功能列表只作线索。

“直接复用”不意味着复制后不检查，也不意味着必须购买某个作者的付费服务。社区开源代码、商业增强模块、教程、云服务和 SDK 条款分别确认。

## 5. 哪些业务仍需自己实现

| 可以复用的能力 | 必须由本项目定义的规则 |
|---|---|
| 登录、Token、RBAC 框架 | 学校／校区范围、成员认证、跑腿资格、敏感字段授权 |
| 后台表格、表单、菜单 | 认证队列、举报处理、订单纠纷、渠道汇总 |
| 上传与对象存储客户端 | 私有证件／聊天／课表附件的访问与保留规则 |
| 支付 SDK、验签、退款接口 | 跑腿费用、结算分配、取消退款、争议冻结、对账和补偿 |
| OCR、Excel 解码 | 学期周次、节次、调课、导入确认、学校模板 |
| WebSocket 传输 | 会话成员、消息持久化与补拉、订单卡片、未读语义 |
| 数据库事务与锁 | 接单竞争、名额容量、唯一预约、幂等业务命令 |

对这些规则保有清楚的业务模型，是后续维护和差异化的基础。框架已经有“订单”类，不代表其取消、退款和履约语义适合本项目。

## 6. 实际接入流程

1. **固定来源。** 保存官方仓库 URL、分支／tag、完整 commit、LICENSE／NOTICE、依赖锁文件和拉取日期；不以搜索结果里的同名 fork 作为源头。
2. **构建最小基线。** 启动账号登录、后台权限、数据库、文件上传；微信真机打开学生端。基线失败先修复或换底座，不继续堆业务。
3. **盘点实际依赖。** Maven 与前端锁文件生成组件清单；检查已知漏洞、许可和不需要的 SDK。检查默认账号、演示密钥、公共文件配置和开放管理端点。
4. **建立适配层。** 微信、存储、OCR 只从统一接口进入业务；SDK DTO 不泄露为本项目公共 API。框架补丁单独记录。
5. **验证关键行为。** 验签回调、跨校权限、数据库与缓存兼容、文件异常、WSS 重连、前端包大小；验证结果附环境和版本。
6. **可重复发布。** 固定镜像与依赖，保留第三方声明和版本清单。上游升级通过独立变更提交，经回归后合入，生产不自动拉取最新分支。

建议在实际代码库维护 `docs/upstream-manifest`，字段包括 `component / official_url / commit_or_version / license_file / reused_paths / local_patches / verified_tests / owner`。架构阶段不伪造尚未选择的版本。

## 7. 复用是否真的省事的验收标准

如果引入组件之后必须重写其核心权限、状态模型和大部分 UI，或需要额外运营一套独立用户／支付系统，应重新比较成本。优先选择“少量适配就能稳定升级”的轮子，而非页面数量最多的项目。

本方案预期降低的是基础工程、后台和第三方接入的重复工作；实际节省多少工时需要以 P0 基线和前两个业务模块的交付记录估算。当前不提供未经实施验证的“复用率 80%”或“几天即可上线”承诺。
