# M04 二手：五个子模块工程设计

版本 v1.1，待实施；遵循公共工程与 A／B／C 验收规范。首次使用线下自提付款，预约、双方确认和其他渠道售出分别记录。

## 共享聚合与边界

M04.01 维护 ListingAggregate 与发布状态模型；.03 和 .04 经聚合方法改变预约／成交状态，不能创建第二套商品状态。商品字段迁移由 .01 统一维护，预约历史表归 .03、确认记录表归 .04。所有修改商品行的命令按同一版本和锁序执行。

内部开发：.01→.02；.01→.03→.04；.05 接入上下文与治理。缓存和搜索只读，聊天消息不作为成交事实。审核决定、下架与成交竞争都重新检查当前状态和内容版本。

## M04.01 出售求购与发布审核状态

**目标与边界：** 管理出售／求购内容、价格、成色、瑕疵和发布状态。只定义发布生命周期，不收款、不管理聊天会话。

**工程结构：** `campus-module-market/.../listing` 下设 ListingController、ListingCommandService、ListingAggregate、ListingValidator、ListingRepository；公开 `ListingCommandApi` 给预约／治理使用。复用上游校验和媒体入口。

**数据与不变量：** 独占 listing 内容字段和内容版本，新增 listing_revision 用于审核快照。owner、school/campus 服务端验证；价格整数分。出售与求购有明确 type，求购关闭不能伪装售出。已成交记录不再编辑为另一商品。

**接口契约：** `saveDraft(type,fields,assetIds,expectedVersion)` 返回 listingId/version；`submitForReview` 返回 contentVersion/reviewState；`applyReview(decision,reviewedVersion)` 返回发布结果；错误包括 NOT_OWNER、INVALID_PRICE、MEDIA_NOT_READY、STALE_REVIEW。

**执行与失败处理：** 草稿与图片绑定同库事务或使用可补偿绑定流程；提交时保存审核内容快照和 outbox。异步审核必须匹配内容版本，用户编辑后旧审核结果不能放行新内容。发布失败保留草稿，重复提交同版本不重复发审核任务。

**依赖与替身：** M01 范围授权、M02 媒体／检查端口、M00 outbox；A 使用通过／拒绝／超时的检查 stub。治理界面不是独立验收前提。

**独立验收：** A：出售帖缺价格或图片未就绪时拒绝提交，草稿仍可编辑；求购按自身字段规则验证。A：审核版本 1 尚在途时编辑成版本 2，版本 1 通过结果不放行版本 2。A：U2 改 U1 内容和跨校发布被拒且无新事件。B：真实媒体与审核接通后只展示通过的对应版本，关闭发布开关不影响历史预约处理。

## M04.02 校园商品检索与详情投影

**目标与边界：** 提供按学校／校区、类型、分类、价格和关键词浏览的公开内容。只读查询，不改商品，不把未审核文本放入搜索结果。

**工程结构：** `.../query` 的 ListingQueryService、SearchQueryNormalizer、ListingReadMapper、PublicListingAssembler；MySQL ngram 复用已选方案。详情与列表共用字段白名单，避免直接序列化实体。

**数据与不变量：** 读取 listing 及允许公开的素材状态；索引覆盖实际查询条件。公开 DTO 不含联系方式、精确预约地点或举报证据。游标绑定排序、筛选和范围，不能用学校 A 的游标绕过学校 B 规则。

**接口契约：** `search(scope,filters,keyword,cursor,limit)` 返回 items/nextCursor；`detail(listingId)` 返回公开详情及当前用户允许操作。非法筛选、深分页、不可见资源分别报稳定错误；不可见详情不泄露隐藏内容。

**执行与失败处理：** 参数化查询、限制关键词与 limit；稳定排序以 createdAt/id 为序，库存状态实时再校验。缓存键包含范围和内容版本，下架通过失效事件与查询状态过滤共同防泄漏。数据库异常返回可重试错误，不输出旧的私有字段。

**依赖与替身：** .01 模型、M01 Scope、M02 公开素材；A 使用真实 MySQL 与固定中文语料，相邻授权以 stub 提供范围。

**独立验收：** A：S1、S2 同名“高数教材”只按请求允许范围返回；单字关键词按定义策略处理且可解释。A：混合新旧条目翻页不重复同 ID，limit 超限受控；下架条目不能从缓存详情继续展示。A：检查 JSON 字段白名单无电话／预约地址。B：10 万条合成数据提供查询计划、环境和耗时记录，以父级容量目标评估，不凭索引存在宣称达标。

## M04.03 预约占用与到期释放

**目标与边界：** 原子创建唯一有效预约，处理取消和超时释放。保留所有历史尝试，不管理双方成交确认。

**工程结构：** `.../reservation` 的 ReservationService、ReservationPolicy、ReservationRepository、ReservationExpiryHandler；调用 ListingAggregate 的 reserve/release 方法，商品行作为并发串行点。

**数据与不变量：** 独占 market_reservation；listing.current_reservation_id 由本用例通过聚合更新。一个商品最多一个有效预约；预约买家不能等于卖家。锁序为 listing→reservation，取消、超时、确认统一使用。

**接口契约：** `reserve(listingId,expectedVersion,key)` 返回 reservationId/expiresAt；`cancelReservation(id,expectedVersion,reason)` 返回当前状态；`expireReservation(id,deadlineVersion)` 用于任务。错误有 ALREADY_RESERVED、SELF_RESERVATION、NOT_PARTICIPANT、STATE_CONFLICT。

**执行与失败处理：** 同事务校验可预约状态、写预约、绑定商品、写事件和到期任务。到期任务基于当前预约 ID 与截止版本，不能释放后来新建预约。超时结果未知时查询原预约；预约 ID 与幂等键共同防重。

**依赖与替身：** .01 聚合、M01 身份、M00.04／05；Clock 可固定。A 使用真实 MySQL，消息端口只记录事件，不要求聊天上线。

**独立验收：** A：100 个同步起跑请求争抢同一商品，恰好一个有效预约，商品绑定与历史一致。A：取消与过期并发只释放一次、发一次有效释放事件。A：旧预约过期任务在新预约成立后到达，新预约保持有效。B：与 .04 确认并发时只能成交或释放之一，不出现 SOLD 商品仍有新活跃预约。

## M04.04 自提确认与关闭归因

**目标与边界：** 区分双方确认成交、卖家其他渠道售出和求购已解决；保留确认来源及版本。线下申报金额不当作渠道核验收入。

**工程结构：** `.../completion` 的 TradeConfirmationService、CompletionPolicy、ConfirmationRepository；通过 ListingAggregate 和 ReservationAggregate 处理状态，输出 MarketCompleted 事件。

**数据与不变量：** 独占 market_confirmation，唯一 `(reservation_id,actor_id,confirmation_type)`；成交归因字段在商品聚合统一更新。双方确认必须关联同一当前有效预约；成交后不能被另一预约覆盖。

**接口契约：** `confirmHandover(reservationId,expectedVersion,key)` 返回双方确认状态／completionSource；`closeListing(listingId,reason,expectedVersion)` 支持 OTHER_CHANNEL_SOLD／WANTED_RESOLVED／WITHDRAWN；错误区分 NOT_PARTICIPANT、RESERVATION_CLOSED、INVALID_CLOSE_REASON。

**执行与失败处理：** 按 listing→reservation 锁序，一次确认只标记本人的确认，满足双方规则后同事务终结预约、标商品 SOLD、写事件。若仍有活跃预约，其他渠道关闭必须明确终结预约并告知对方，不能暗中留下可确认状态。失败不部分标成交。

**依赖与替身：** .01/.03 共享聚合与查询、M00 事务；A 配置真实预约夹具，统计消费者使用计数 stub。

**独立验收：** A：单方确认只记录一次，不计双方成交；第二方确认后恰好一条完成事件。A：重复确认、非参与人确认、过期预约确认均不能额外成交。A：其他渠道售出归因正确且不产支付单／平台收入。B：预约取消与双方最后确认并发，终态可解释并与统计一致；事后人工修正产生新记录而非删除历史。

## M04.05 交易上下文、举报与运营命令

**目标与边界：** 为消息、举报与运营提供最小可用的商品上下文和经过授权的管理命令。会话和案件由对应模块拥有。

**工程结构：** `.../integration` 下设 MarketContextProvider、MarketResourcePolicy、MarketAdminCommandService；在启动层注册 provider，不让身份模块直接导入 market 实现。

**数据与不变量：** 读取商品／预约快照；通过 .01/.03/.04 公开命令变更，不新增同义投诉或消息表。案件引用包括 resourceId、contentVersion、必要公开快照与受限证据引用。

**接口契约：** `getConversationContext(listingId,actor)` 返回可见标题、缩略图、参与关系；`prepareReportContext` 返回最小证据范围；`adminTakeDown(listingId,caseId,expectedVersion,reason)` 返回效果／不适用原因。每个管理命令验证学校范围和操作角色。

**执行与失败处理：** 商品下架先禁止新预约，已有预约按规则显式取消或保留履约，不抹除历史。运营命令以 caseId/actionId 幂等，变更与日志事件同事务；推送失败不回滚治理决定。聊天内旧卡片重新拉取状态。

**依赖与替身：** .01–.04、M01 ResourcePolicyPort；M07/M09 使用契约 stub，即可独立验证消息上下文和治理权限。

**独立验收：** A：普通浏览者只能获得公开卡片，不能得到预约联系方式；O2 无法处理 S1 商品。A：同一 case action 重放仅产生一次下架效果；并发成交时治理命令不把已成交历史改成未售。B：举报到运营下架后消息卡片显示最新不可预约状态，同时双方历史消息仍按成员权限可查。

## 大模块集成验收

以两个学生完成草稿→审核→检索→预约→私聊→双方确认；分别重跑取消、超时、其他渠道售出、举报下架。检查公开／私有字段、商品与预约终态、事件与统计来源一致，不产生线上付款假象。
