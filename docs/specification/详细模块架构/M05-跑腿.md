# M05 跑腿：详细模块架构

版本：v1.1，2026-09-17。本文为实施契约，所有类、表和方法均为拟定设计；验收尚未执行。共同约束见《00-工程约定与独立验收规范》，资金规则以 M08 与父架构为准。

## 总览、数据归属与内部依赖

本模块拥有 `backend/campus-module-errand/`，提供任务报价、创建、接单、履约、取消和争议协调。它持有履约事实，通过 Finance API 发起资金命令，不写上游 pay 表或任何 `fin_*` 表。学生页面由 M10 集成，客服案件由 M09 拥有。

| 子模块 | 唯一写入责任 | 共享规则 |
|---|---|---|
| M05.01 | `errand_price_rule` 的不可变发布版本、报价记录 | 已下单价格和取消规则不可追溯改写 |
| M05.02 | `errand_order` 聚合模型、创建与支付衔接命令 | 其他子模块通过该聚合的合法转移更新各自负责状态 |
| M05.03 | 接单命令、`errand_runner_load` 增占与共享释放方法 | 每个任务最多一个有效接单者，每个跑腿员不超并发额度 |
| M05.04 | `errand_evidence`、取件／送达／完成命令 | 完成不能等同已到账 |
| M05.05 | 取消／争议命令及订单案件关联 | `ops_case` 仅 M09 写；权威资金冻结仅 M08 写 |
| M05.06 | 到期扫描进度、只读运营查询 | 调用上述命令补偿，不直接修改业务状态 |

`errand_status_log` 由共享聚合写入器追加，每次合法状态变更在同一事务产生一次；不为不同子模块复制日志表。M05.02 维护聚合骨架，其他子模块拥有相应领域方法的实现责任。内部依赖为 .01 → .02 → .03 → .04；.05 使用 .02/.03 与 M08；.06 调用 .02–.05。涉及共享类的修改按方法责任合并，不能各自替换整个聚合。

统一事务次序：接单先由 M01.05 `assertForAccept` 在调用方事务锁定资格行，再锁业务订单、跑腿员负载；需要财务动作时继续进入 M08 的资金锁次序。完成／取消仅按订单→负载→资金控制记录执行，不反向重新锁资格。M01 停用资格事务共用资格行锁，但不反向锁任务；未完成任务通过之后的有条件命令处理。跨域使用同一个 Spring 事务管理器，Finance API 加入当前事务，M08 不反向锁跑腿表。批处理逐单提交，外部支付、消息、文件网络操作不放入持锁事务。

## M05.01 计价与规则快照

**目标与边界：** 根据学校、校区、任务类型、粗粒度取送区域和规格计算价格。首期使用明确规则，不自动推测距离或临时议价。规则包含服务费、跑腿员报酬、附加费、取消条件、履约期限和舍入方式；发布新版本不影响历史订单。

**工程结构（目录／类／分层）：** `controller/app/ErrandQuoteController` 校验输入；`application/pricing/QuoteService` 编排授权与规则选择；`domain/pricing/PriceRule`、`PriceQuote`、`MoneyBreakdown` 实现确定性计算；`infrastructure/pricing/PriceRuleRepository` 持久化。管理员发布规则入口调用同一 application，不能靠直接 SQL 配价。可注入 Clock 固定有效期测试。

**数据与不变量：** 规则按校区、任务类型、version 唯一，已发布版本只追加替代；同一生效时点只能选出一条确定规则。报价保存 quoteId、owner、规则版本、规范化输入摘要、各项金额、币种、过期时间；不保存多余取件码。所有金额为整数分，报酬和平台分配遵守该版本约定，负数、溢出和不支持币种拒绝。

**接口契约（输入输出错误）：** `POST /app-api/campus/v1/errand-quotes` 输入校区、类型、规格，身份来自会话；输出 quoteId、expiresAt、总价与明细、规则摘要。内部 `QuoteApi.validateForOrder(quoteId,userId,inputDigest)` 返回不可变快照。错误含 `SERVICE_UNAVAILABLE`、`UNSUPPORTED_TASK`、`QUOTE_EXPIRED`、`QUOTE_INPUT_CHANGED`；不接受前端覆盖金额。

**执行与失败处理（事务与外部边界）：** 报价生成仅短事务写入记录，规则读取以有效版本完成计算。提交订单时再次验证报价归属、摘要和有效期；有效报价按已展示快照履行，校区紧急停服则明确拒绝新单。校区配置服务不可用时不使用零价兜底；无外部支付调用。

**依赖与替身：** 依赖 M01 校区授权、M09 服务开关与规则发布权限、M00 金额/时间工具；A 使用版本化身份与配置 stub、真实 MySQL。价格是本域规则，不从通用商城订单复用不匹配的促销逻辑。

**独立验收：** A：① 固定规则与 Clock 报价两次，断言明细一致、数据库规则版本一致、支付调用为零；② 用 U2 消费 U1 报价或修改规格，断言拒绝且无订单写入；③ 发布新版本后用仍有效旧报价下单 stub，断言返回旧快照；边界分数费率检查按约定舍入。B：与 .02 联调，订单与报价金额完全一致，过期报价不生成支付关联。C：真机展示明细及到期重报交互；本项不依赖支付权限，不能据此宣称收费已可上线。

## M05.02 订单创建与支付衔接

**目标与边界：** 建立唯一业务订单及付款关联，只有可信付款结果才开放接单。负责 `ErrandOrder` 聚合状态机与支付结果入口；不在订单表复制微信支付状态作为另一资金真相，也不直接调用微信 SDK。

**工程结构（目录／类／分层）：** `controller/app/ErrandOrderController`；`application/order/CreateErrandService`、`PaymentResultHandler`；`domain/order/ErrandOrder`、`ErrandTransitionPolicy`；`infrastructure/order/ErrandOrderMapper`、状态日志与事件存储。订单查询返回履约状态，资金展示由 Finance 查询 DTO 组合，失败时标“资金状态待查询”。

**数据与不变量：** `errand_order` 保存 requester、school/campus、价格与取消规则快照、paymentBusinessRef、期限、version；clientRequestId 在用户与创建操作范围唯一。首期同一订单只允许一个可支付关联，不因刷新重建。地址明细及联系方式与大厅投影分离。`WAITING_PAYMENT → OPEN` 仅接受与订单金额、业务 ID 匹配的可信事件。

**接口契约（输入输出错误）：** `POST .../errands` 输入 quoteId、规格、授权私有信息与幂等键，返回 orderId、履约状态、paymentId、nextAction。`ErrandApi.applyPaymentResult(event)` 输入 M08 事件标识、金额及关联，输出 applied/duplicate/compensationRequired。错误包括 `IDEMPOTENCY_CONFLICT`、`QUOTE_INVALID`、`PAYMENT_DISABLED`、`STATE_CONFLICT`；前端成功回调仅触发查询。

**执行与失败处理（事务与外部边界）：** 同一事务保存订单、调用 `FinanceApi.createPayment` 保存资金关联与 guard、写 outbox；Finance 加入事务且此命令不进行网络预支付。提交后由 M08 获取渠道参数。支付通知消费标记、状态转移和 outbox 同事务。若订单已关闭而可信付款晚到，保留关闭，按稳定补偿键申请退款；订单不重新进入大厅。跨域调用失败整体回滚。

**依赖与替身：** .01 报价、M01 身份、M02 私有附件、M08 创建付款与查询、M00 幂等/outbox。A 以 Finance 契约 stub 验证调用与失败，真实 MySQL 验证订单唯一性；B 必须使用真实 Finance 验证传播事务，stub 成功不能证明跨模块原子性。

**独立验收：** A：① 同键并发创建，断言一个订单、一次状态日志、各响应同 orderId；② Finance stub 抛异常，断言订单/幂等成功记录/outbox 均无提交；③ 重放已验证付款事件，断言仅一次 OPEN 与一次可接单事件。B：付款创建后故障回滚应同时删除订单和关联；关闭订单后投递付款成功，断言大厅不可见且只建一笔补偿退款。C：获批小程序完成小额支付，关闭客户端后后台仍能进入 OPEN；取消支付不能开放接单。

## M05.03 任务大厅与并发接单

**目标与边界：** 提供真实可接任务列表，保证单个任务不被重复领取、跑腿员不超过并发额度。大厅查询只是候选，接单命令重新验证身份、状态、时限和范围。任务列表不暴露精确地址、手机号或取件码。

**工程结构（目录／类／分层）：** `controller/app/ErrandHallController`；`application/accept/AcceptErrandService`；`domain/accept/AcceptancePolicy`、共享 `RunnerLoadService`；`infrastructure/accept/RunnerLoadMapper` 与大厅只读投影。释放额度是该子模块公开的事务方法，由完成或取消用例调用；禁止其他子模块自行减计数。

**数据与不变量：** `errand_runner_load` 按 runner 与适用学校范围唯一，activeCount 不小于零且不超批准额度；订单记录 runner 与 activeAssignment 标记。接单、订单占用标记和计数同事务。释放以订单占用标记由真变假为前提，重复完成不会重复减数。负载缓存只作展示，不决定能否接单。

**接口契约（输入输出错误）：** `GET .../errands/available` 输入授权校区、游标和有上限的分页；输出脱敏任务。`POST .../errands/{id}/accept` 输入幂等键和 expectedVersion，runner 来自会话，返回接单状态与允许访问的履约字段。错误含 `RUNNER_INELIGIBLE`、`SELF_ACCEPT_FORBIDDEN`、`ORDER_TAKEN`、`LOAD_LIMIT`、`ORDER_EXPIRED`。内部 `releaseAssignment(orderId)` 在已有事务中返回是否释放。

**执行与失败处理（事务与外部边界）：** 先调用 M01.05 `assertForAccept` 加入当前事务锁定资格行并校验，再锁订单、锁/幂等初始化负载行，检查当前状态后同时更新订单与计数、日志和 outbox。固定次序为资格→订单→负载，完成/取消释放仅用订单→负载，不反向锁资格。停用资格也锁同一资格行，停用事务不反锁任务；先提交停用则接单拒绝，先提交接单则后续停用通过有条件命令处理已有任务，不能伪造接单未发生。死锁有限重试整笔事务；通知失败不撤销已提交接单。

**依赖与替身：** .02 聚合、M01 接单资格、M00 事务/outbox，M07 异步通知；A 使用身份 stub 配置不同额度，数据库必须是真实 MySQL/InnoDB。消息 stub 失败不影响核心结果。M05.04/.05 依赖此处额度释放契约。

**独立验收：** A：① 屏障同时让 R1/R3 接同单，断言一个成功、一个 runner、总增占为一；② R1 额度一并发接两单，断言仅一单归属且计数一；③ requester 自接、R2 停用、U3 跨校分别拒绝，无计数和事件变化。B：真实完成/取消重放后负载只释放一次；接单与 M01 停用屏障竞争，断言先停用则拒绝、先接单则保留已成立任务且后续停止接新单，无资格/任务反向锁等待。C：两台真机并发抢单并对照数据库，落败端刷新真实状态且看不到私有字段；此测试不替代真实数据库并发证据。

## M05.04 履约证据与完成

**目标与边界：** 记录取件、开始配送、送达和完成的可审计事实，支持用户确认及规则允许的自动确认。送达证据不自动证明无争议；完成仅产生应付结算申请，不承诺跑腿员已到账。

**工程结构（目录／类／分层）：** `application/fulfillment/FulfillErrandService`、`CompleteErrandService`；聚合上的 start/deliver/complete 方法；`domain/fulfillment/EvidencePolicy`；`infrastructure/fulfillment/ErrandEvidenceMapper`。证据通过 M02 媒体绑定 API 引用，HTTP controller 不接收任意公网 URL。到期触发由 .06 调用本服务。

**数据与不变量：** `errand_evidence` 保存 order、uploader、用途、assetId、时间与内容摘要；媒体归属和订单成员关系需核验。`DELIVERED` 保存送达时间和按下单规则计算的确认截止时间。COMPLETED 只发生一次；释放负载、完成日志及结算请求事件共事务，不因用户重复点击生成第二次分配。

**接口契约（输入输出错误）：** `POST .../errands/{id}/start|deliver|complete` 分别限定有效 runner、runner、requester；deliver 输入经授权的证据引用，complete 输入版本和幂等键。返回履约状态、资金状态查询入口、争议入口。内部 `completeIfEligible(orderId,clock,reason)` 用于自动确认。错误为 `NOT_ASSIGNED_RUNNER`、`EVIDENCE_INVALID`、`WRONG_STAGE`、`DISPUTE_OPEN`、`CONFIRMATION_NOT_DUE`。

**执行与失败处理（事务与外部边界）：** 文件先上传并校验，短事务内绑定证据、更新订单与日志；媒体绑定必须支持同事务元数据关联，文件上传不持业务锁。完成锁订单与负载后释放占用并写结算请求 outbox，M08 用业务唯一键生成结算。自动确认重新检查已送达、期限、必要提醒记录和争议；消息供应商是否实际送达不能伪造为已提醒。争议等待期间结算保持不可打款。

**依赖与替身：** .02 状态机、.03 额度释放、M02 媒体、M08 结算事件、M07 提醒状态；A stub 媒体/提醒，真实 MySQL 验证原子性。B 验证结算延迟消费仍继承 M08 guard 冻结，不能因订单完成丢失争议控制。

**独立验收：** A：① 非接单者用有效图片 deliver，断言拒绝且无证据关系；② requester 并发重复 complete，断言一次完成、一次额度释放、一次结算请求；③ 将 Clock 推过期限但存在争议或缺提醒前提，断言不自动完成。B：完成事务回滚不释放负载、不发结算；完成后先受理争议再消费结算事件，结算必须冻结。C：真机上传失败可重试且不显示已送达；真实私有存储不能被非成员读取，真实小额履约后分别核对“完成”“待结算”“到账”。

## M05.05 取消争议与同步冻结

**目标与边界：** 根据订单快照执行取消和争议处理，使用户看到受理成功时立即存在权威资金控制。案件正文、处理权限和决定由 M09 拥有；M05 负责履约合法性与订单案件关联，M08 负责冻结、退款和结算后果。

**工程结构（目录／类／分层）：** `application/dispute/ErrandResolutionService`，`domain/dispute/CancellationPolicy`、`ResolutionDecision`；订单聚合实现 cancel/attachCase/applyResolution。M09 的案件协调服务调用 `ErrandApi.openDispute/applyResolution`，后者调用 Finance API；M05 不反向依赖 M09 实现或直接写 `ops_case`。统一 coordinator 在同一个数据库事务中串联这些命令。

**数据与不变量：** 订单保留 caseId、争议标记、状态历史与原规则快照；`fin_business_fund_guard` 是资金冻结唯一真相。caseId/reason 对应独立冻结原因，多案件不能因关闭一案清空全部冻结。无结算时也能冻结。已进入执行阶段的转付记录不会被本地取消删除或改为未支付。

**接口契约（输入输出错误）：** 取消输入 orderId、expectedVersion、reason、幂等键；案件打开输入服务端案件 ID 和授权主体；裁决输入 decisionId、动作、已核准退款金额与复核信息。返回履约状态、freezeApplied、payoutExecutionState、退款处理状态。错误含 `CANCEL_NOT_ALLOWED`、`CASE_VERSION_CONFLICT`、`REFUND_REVIEW_REQUIRED`；出现转付执行中时返回明确受理结果，不能笼统承诺“款项已冻结”。

**执行与失败处理（事务与外部边界）：** M09 受理案件、M05 关联与 M08.freezeSettlement 加入同一事务，失败全部回滚；禁止 REQUIRES_NEW 或跨线程冻结。锁订单、必要负载，再锁 finance guard；退款预占可同事务申请，渠道退款提交后异步执行。裁决解冻仅关闭自己的冻结原因并再检查其它原因。已付款后取消进入退款待处理，尚未付款则申请关单；支付晚到走原单补偿。通知只在提交后执行。

**依赖与替身：** .02 聚合、.03 释放、M08 guard/退款，M09 是上层调用方。A 使用事务感知的 Finance stub、真实 MySQL 检查本域回滚；B 必须三模块真实实现验证同一事务，普通内存 mock 无法证明冻结原子性。

**独立验收：** A：① 冻结 stub 抛错，取消/案件关联不得提交；② 重放同裁决不重复释放额度或申请退款；③ 越权客服、过期版本拒绝且日志无成功动作。B：停止所有事件消费者后受理争议，断言案件和 guard 同时存在且新打款零调用；注入提交前异常，两者皆回滚；与打款并发只允许“先冻结禁止打款”或“已执行需查询”之一。C：真实渠道受理后申请取消，页面持续显示待核实，最终状态依据查单，不能把撤销 API 受理等同撤销完成。

## M05.06 到期补偿与运营查询

**目标与边界：** 找出付款期限、接单期限、确认期限到达的任务及业务事件遗漏，调用已有命令完成补偿；向用户与授权运营提供可解释的履约时间线。此子模块不承担支付渠道查询或财务对账，也不自行绕过状态机改表。

**工程结构（目录／类／分层）：** `application/recovery/ErrandExpiryJob`、`ErrandRecoveryService`；`application/query/ErrandQueryService`；`infrastructure/query/ErrandReadMapper` 和 M00 任务租约适配。扫描采用校区/状态/到期时间索引与 keyset 分页；每项独立执行，运营导出走受控异步任务。

**数据与不变量：** 任务游标和重试信息属于恢复记录；订单终态仍由 .02/.04/.05 命令写入。幂等键根据 orderId、任务类型及期限版本生成，不能每次扫描随机生成。后台列表只读，学校/校区范围从角色授权交集构造，私有信息按案件及用途单独授权。查询延迟不得通过写假状态“修复”。

**接口契约（输入输出错误）：** `ErrandRecoveryApi.runBatch(taskType,cursor,limit,now)` 返回 scanned/applied/skipped/retryable；`GET /admin-api/campus/v1/errands` 返回分页概况，详情组合状态日志和 Finance 只读结果。人工重跑输入命令类型、目标、原因、版本，返回 jobId。错误为 `SCOPE_DENIED`、`RECOVERY_NOT_APPLICABLE`、`DEPENDENCY_UNAVAILABLE`；无跨域 SQL 修改入口。

**执行与失败处理（事务与外部边界）：** 扫描不长持锁；执行时重新锁订单并检查当前状态与期限，抢到接单或人工完成后任务可安全跳过。租约过期支持重领，旧执行者必须凭 fencing token 交任务结果。业务已提交但任务 ACK 丢失时重跑返回原业务结果；失败进入有界退避和人工队列。关闭新业务开关不关闭历史订单恢复、退款和查询。

**依赖与替身：** .02/.04/.05 命令、M01 数据范围、M08 财务查询、M00 Clock/租约/outbox。A 使用真实 MySQL 和命令 stub 验证选择范围及调用键；B 使用真实聚合验证并发终态。C 涉及真实支付的补偿复用 M08 真实资金验收，不在本模块另建假查单器。

**独立验收：** A：① 固定三种期限及学校样本，推进 Clock，断言只选到期允许范围、稳定命令键；② 任务处理一半宕机重启，断言剩余可恢复且成功项不重复产生业务影响；③ O1 访问 S2 详情/导出均拒绝，无私有字段泄漏。B：到期取消与接单屏障竞争，断言终态一致、计数不负；冻结存在时自动完成不越过规则；暂停 worker 恢复后历史待处理单最终收敛。C：真机前后台切换显示后台实际结果，真实支付异常用同原单核对，留脱敏渠道与数据库证据。
