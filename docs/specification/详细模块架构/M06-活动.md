# M06 活动：五个子模块工程设计

版本 v1.1，待实施；沿用公共工程与验收规范。首次实现免费活动，付费活动仅预留边界，不能用模拟支付验收上线。

## 共享聚合与开发顺序

M06.01 拥有 ActivityAggregate 与活动规则；.02 拥有 RegistrationAggregate 与容量变更入口，.03 通过该入口提升候补；.04 管签到；.05 调用前述命令批量关闭／释放。活动容量不另存一份 Redis 权威数值。

开发顺序 .01→.02→.03，.04 与 .05 在契约稳定后独立开发。统一写入锁序 event→registration→checkin，批处理每次限定数量。事件是提醒和读模型来源，不是占位成功依据。候补序号分配是共享的纯领域策略，由 .02 在 event 锁内执行；.03 的提升服务调用 .02，.02 不反向调用提升服务，避免构造依赖循环。

## M06.01 活动发布与参加规则

**目标与边界：** 管理标题、地点、时间、名额、报名截止和参加范围，以及审核发布生命周期。不在本模块接收报名和分配名额。

**工程结构：** `campus-module-activity/.../event` 中 ActivityController、ActivityCommandService、ActivityAggregate、EligibilityPolicy、ActivityRepository；复用媒体、认证和内容检查端口。

**数据与不变量：** 独占 activity_event 内容、规则、内容版本；时间满足报名截止不晚于开始，结束晚于开始，capacity 为非负有限整数。已占用名额由 .02 修改；减少容量不得低于有效占位数。

**接口契约：** `saveEventDraft(fields,expectedVersion)`、`publish(eventId,contentVersion)`、`changeEvent(eventId,patch,expectedVersion)` 返回规则／审核状态；`getEligibilityRules` 返回版本化规则。错误包括 INVALID_TIME、CAPACITY_BELOW_OCCUPIED、STALE_REVIEW。

**执行与失败处理：** 审核只放行对应内容版本。已有报名时变更时间地点需要记录变更事件和通知任务；重大变更不能悄悄覆盖已报名时看到的内容。通知故障独立重试，规则修改本身有审计。

**依赖与替身：** M01 学校／主办方授权，M02 素材检查，M00 outbox；A 使用资格与审核 stub，以及固定 Clock。

**独立验收：** A：倒置时间与容量低于已占用数的修改拒绝且零状态变更。A：旧审核结果不能发布新版本；其他学校运营无法替主办方编辑。B：改地点后报名记录保留原规则版本与新的通知事件，前端详情展示最新地点和变更提示。

## M06.02 报名资格与名额占用

**目标与边界：** 判断资格并原子分配名额，是正式报名、取消释放、候补提升共同调用的容量入口。

**工程结构：** `.../registration` 的 RegistrationService、RegistrationAggregate、CapacityPolicy、RegistrationRepository；`CapacityCommandApi` 只在调用方事务内工作，不允许绕过规则直接改 occupied。

**数据与不变量：** 独占 activity_registration 的状态与容量操作；唯一 event/user。有效占位数与 event.occupied 一致，范围为 0..capacity。每次状态迁移记录 registration version 与 operationId；重新报名复用成员关系而非插入重复占位。

**接口契约：** `register(eventId,key)` 返回 CONFIRMED／WAITLISTED 及 registrationId；`cancelRegistration(id,expectedVersion)` 返回释放结果；`confirmCandidate(id,eventVersion)` 供 .03 使用。错误区分 NOT_ELIGIBLE、REGISTRATION_CLOSED、ALREADY_CHECKED_IN、STATE_CONFLICT。

**执行与失败处理：** 先锁 event，再查锁该用户 registration，重新校验时间／资格／取消状态，插入或迁移状态并原子改变 occupied。报名动作进入候补后不计占位；释放和候补唤醒事件同事务。重试不会重复增加容量。

**依赖与替身：** .01 活动、M01 资格、M00 幂等；A 真实 MySQL，资格端口固定通过／拒绝，使用共享候补排序纯策略。B 联调 .03 提升服务，不把提升服务注入报名服务。

**独立验收：** A：10 名额、100 并发用户恰好最多 10 个 CONFIRMED，occupied 与 SQL 计数一致。A：同用户重复／并发报名不占两个名额；截止瞬间由服务端 Clock 决定，客户端时间不生效。A：取消重复执行只减一次。B：与取消整场和候补提升竞争不超额，不出现活动已取消却新增成功报名。

## M06.03 候补队列与自动提升

**目标与边界：** 给候补排定顺序，在有空位时可靠提升合格成员。它不独立维护容量真相，必须调用 .02 同事务容量入口。

**工程结构：** `.../waitlist` 的 WaitlistService、WaitlistPromoter、WaitlistOrderPolicy、WaitlistReadMapper；由名额释放事件和补偿扫描触发，不要求消息渠道在线。

**数据与不变量：** 候补状态复用 registration；queue_seq 由 event 行上的递增序号在锁内分配。退出后重新候补进入队尾。为防长时间占锁，每次处理有限候选；跳过不合格人记录原因而非静默消失。

**接口契约：** 入队命令归 M06.02 的 register，使用共享排序策略分配 seq，本项不再暴露第二个入队写入口。`promote(eventId,triggerId,batchSize)` 返回 promoted/skipped/remaining；`getWaitlistPosition` 返回当前估计位置及更新时间，不承诺未来一定转正。

**执行与失败处理：** promoter 锁 event，按 seq 选择候选，逐一经 .02 资格／容量检查迁移为 CONFIRMED；记录与通知 outbox 同事务。重复唤醒和 worker 重启可安全重做；活动截止或取消时停止提升。

**依赖与替身：** .02 CapacityCommandApi、M01 当前资格、M00 任务；A 用真实数据库、固定资格 stub，通知只校验 outbox。

**独立验收：** A：第一个候补资格失效，释放一名额后提升下一个且记录跳过原因。A：两个 worker 同时提升只占一次，重复事件不重复发有效转正通知。A：提升事务中断后数据库回滚，重跑不丢队列成员。B：活动取消与提升并发时已取消活动不再产生新有效占位；位置查询与实际序列规则一致。

## M06.04 签到凭证与签到记录

**目标与边界：** 对已确认报名执行签到，防止越权、重复扫码和过期凭证。候补不能通过拿到活动二维码直接签到。

**工程结构：** `.../checkin` 的 CheckinTicketService、CheckinService、CheckinPolicy、CheckinRepository；凭证签名复用成熟密码组件，密钥通过配置注入。前端不决定报名状态。

**数据与不变量：** 独占 activity_checkin；唯一 registrationId。凭证绑定活动、报名人／允许场景、有效期与 nonce，公开二维码不能暴露名单或身份证明。核验方必须有该活动签到权限。

**接口契约：** `issueCheckinTicket(registrationId)` 返回短期票据／expiresAt；`verifyAndCheckin(ticket,operator,key)` 返回 CHECKED_IN／ALREADY_CHECKED_IN；错误为 TICKET_EXPIRED、NOT_CONFIRMED、OPERATOR_FORBIDDEN、EVENT_CLOSED。

**执行与失败处理：** 验证票据后按统一锁序重新检查活动与报名状态，再写唯一签到记录。重复扫码返回原签到时间；网络超时重试不生成另一记录。取消与签到竞争按配置确定能否退出，不能先签到后被后台无审计删除。

**依赖与替身：** .01/.02 数据端口，M01 主办方授权，Clock／签名提供者；A 可本地固定密钥，B 验证真实报名，C 真机扫码。

**独立验收：** A：过期、篡改、跨活动票据均拒绝且零签到；候补票据无效。A：十次重放返回同一签到记录；未经授权的 O2 扫码不能查到 S1 姓名。B：退出报名与签到并发形成一种合法终态。C：真机二维码读取与失败提示明确，不因相机成功扫描就显示签到成功。

## M06.05 活动取消、截止与批量善后

**目标与边界：** 处理截止、活动结束、主办方取消和后续批量报名关闭／通知，保证任务失败可续跑。不以一个大事务锁全场用户。

**工程结构：** `.../lifecycle` 的 ActivityLifecycleService、EventCancellationCoordinator、RegistrationBatchCloser、LifecycleReconciler；由可注入 Clock、定时器和运营命令触发。

**数据与不变量：** event 生命周期通过 .01 聚合修改；新增 activity_lifecycle_job 保存 eventVersion、cursor、attempt、终结原因。报名变更只调用 .02，单用户处理幂等；任务进度不等于全部通知送达。

**接口契约：** `cancelEvent(eventId,reason,expectedVersion,key)` 返回 CANCELLING/jobId；`getCancellationProgress` 返回处理总数／成功数／待处理；`closeExpiredRegistrations(batch)` 返回游标。付费记录意外出现时转人工异常，不按免费流程假装退款。

**执行与失败处理：** 首个事务将活动置 CANCELLING，阻止报名／提升；随后按游标短事务关闭报名并释放容量、产生通知事件。每批确认提交后推进进度，结束检查剩余有效报名再置 CANCELLED。新旧任务根据 eventVersion 拒绝过期操作。

**依赖与替身：** .01–.03、M00 worker；A 用真实报名数据和通知 stub，不依赖微信提醒送达。

**独立验收：** A：处理 1,000 条报名中途退出，续跑后各记录只关闭一次、占位归零，候补也终结。A：取消命令重复返回同一作业；取消期间新报名／候补提升拒绝。A：推送服务失败不回滚已关闭报名，通知可重试。B：运营与主办方同时取消只形成一个可追溯决定，统计最终与有效报名一致。

## 大模块集成验收

完成发布、多人报名、候补、退出、转正、签到与整场取消；每个阶段校验 occupied 等于有效占位 SQL 计数。截止任务、候补 worker 和用户操作并发时仍保持唯一报名与合法终态。
