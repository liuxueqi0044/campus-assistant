# M07 消息：五个可独立交付子模块

本文件是待实施工程契约，遵循 [工程约定与独立验收规范](00-工程约定与独立验收规范.md)。范围是业务私聊与通知中心，采用 Spring WebSocket 和客户端原生 WSS；不搭建完整社交平台，不混用 Socket.IO 协议。

## 共享数据、内部边界与依赖

- 代码位于 `backend/campus-module-message/`。`.01` 拥有 `msg_conversation` 与成员资格字段；`.02` 负责消息正文与序号分配；`.04` 负责 `msg_member.read_seq`、补拉查询；同一 Conversation 聚合和仓储共享，不复制多套会话状态。
- `.02` 写 `msg_message`，唯一 `(conversation_id,seq)` 与 `(conversation_id,sender_id,client_message_id)`；撤回／审核变更时由 .02 同事务追加 `msg_message_change`，.04 拥有其补拉协议与查询，不直接改正文。`.05` 写 `msg_notice`、通知投递记录。WSS 路由 `.03` 不写第二份消息真相来源。
- 内部契约为 `ConversationApi`、`MessageApi`、`NotificationApi`、`BusinessContextProvider`。各业务实现最小上下文 provider，启动模块注册；消息不依赖商品／订单实现。上下文卡片保存必要快照，点击后重新查询真实业务状态。
- 依赖 M00、M01、M02；可先使用授权／文件／业务上下文 stub 验收。持久化消息与 outbox 同事务；WSS 只提供及时送达提示，断线和后台恢复依靠 HTTP 补拉。
- 对隐私与审核删除保留占位和 seq。未读数统计“对当前成员可见、需要计未读、非本人发送且 seq 大于 read_seq”的记录，不能直接以 last_seq 减 read_seq。

## M07.01 会话成员与上下文

**目标与边界：** 仅为合法业务参与人创建唯一会话，并统一历史、发送与订阅资格。首期支持双人业务私聊；不允许客户端直接传任意成员集合创建群聊，也不自动给校园运营加入学生会话。

**工程结构：** 拟建 `ConversationApplicationService`、`domain/Conversation`、`ConversationRepository`、`api/BusinessContextProvider`。请求业务引用 → provider 解析对端及允许动作 → 规范化双方 ID 与上下文键 → 事务查建会话和成员。拉黑、发送限制通过明确策略接口执行，资源授权 provider 为 M01 返回成员资格。

**数据与不变量：** `msg_conversation` 保存 context_type/id、school_id、canonical_pair、status、version；唯一 context 与规范成员对防止重复房间。`msg_member` 唯一 conversation/user，区分 READ、SEND、SUBSCRIBE 权限及有效范围；关闭发送不删除历史。业务学校来自服务端上下文，不能由请求伪造；参与人身份与权限不因切浏览校区改变。

**接口契约：** `POST /conversations {contextType,contextId}` 返回 conversationId、成员展示摘要、capabilities；内部 `assertMember(actor,id,action)`；错误 `CONVERSATION_NOT_ACCESSIBLE/CONTEXT_UNAVAILABLE/MESSAGE_SEND_RESTRICTED`。不向陌生人返回手机号、收货地点或上下文私有字段。

**执行与失败处理：** 同一上下文并发创建靠唯一键回查既有会话，不产生孤立成员。加入／撤销权限和状态事件同事务；业务关闭或封禁到达时应用版本条件，旧事件不能重新开放发送。发送和订阅按当前权威资格检查；会话列表缓存失效失败不放宽单资源权限。已删除上下文仍按明确历史保留策略提供必要记录。

**依赖与替身：** 依赖 M00、M01，Market／Errand 等 context provider 使用固定样例。首次仅双人会话，后续活动群聊需新增成员加入、退出与历史可见范围规则，不能直接放宽现有接口。

**独立验收：** A：U1/U2 为同商品并发建会话只一条会话及两条成员；U3 伪造双方 ID 无效且不建会话；非成员历史、发送和订阅断言均拒绝。B：商品真实 provider 返回最小快照，商品关闭后按策略停止新发送但保留获权历史；普通 O1 查聊天无案件权限仍拒绝。C：真机从同商品反复进入为同一会话，切换学校不获得他人会话，展示不包含订单私有取件信息。

## M07.02 消息持久化与顺序

**目标与边界：** 确保客户端重试只产生一条消息，服务器给出可靠会话顺序。此项管理文本、已获准图片引用和业务卡片记录；不以 WSS 已发送或客户端本地显示作为保存成功证据。

**工程结构：** 拟建 `MessageApplicationService`、`MessageRepository`、`MessageContentPolicy` 与 `MessageSentHandler`。校验身份／成员／内容 → 事务锁 Conversation → 查 clientMessageId → 分配 nextSeq → 写消息和 outbox → 返回服务器确认。会话聚合的计数器在同事务递增，发送通道统一调用本用例，禁止 HTTP 与 WSS 各写一套逻辑。

**数据与不变量：** `msg_message` 保存 sender、seq、client_message_id、bodyType、受限正文或 assetId、状态和时间；两组唯一键保证顺序与去重。同键不同正文返回冲突。服务器 seq 只在可接受消息正式保存时分配，复核未通过内容不返回发送成功；内容删除改成 tombstone，不物理移除序号。不得按毫秒时间戳当唯一顺序。

**接口契约：** `POST /conversations/{id}/messages {clientMessageId,type,content}` 返回 messageId、seq、serverTime、replayed；WSS send 同结构。错误 `CLIENT_MESSAGE_CONFLICT/MESSAGE_SEND_RESTRICTED/MESSAGE_CONTENT_REJECTED/MESSAGE_REVIEW_REQUIRED`；未完成检查的图片不能直接发送公开链接。

**执行与失败处理：** 内容检查在短事务前完成并绑定 hash／版本，提交时核对未变；需人工复核返回明确未发送状态，不悄悄排为已送达。消息与 outbox 原子提交，提交成功响应丢失后重试回查原记录。事务回滚不保留错误 seq 或成功事件；发送限流拒绝不追加记录。撤回或审核删除也发带原 seq 的版本化变更事件。

**依赖与替身：** 依赖 .01、M00 幂等／outbox、M02 文件与内容检查。A 使用真实 MySQL 及内容策略 stub；消息正文加密／脱敏复用已验证组件，不自创密码算法。

**独立验收：** A：同 clientMessageId 50 并发仅一消息、一 seq、一事件，响应均指向同记录；同键异体返回 409；100 条不同消息并发 seq 唯一且查询顺序稳定。B：提交后断连接再重试不重复显示，未成员发送零写入；图片绑定无权或未检查时拒绝；outbox 提交失败使消息同步回滚。C：微信弱网重试与前后台切换后原 clientMessageId 保留，最终服务器仅一条记录；无法联网时本地状态显示待发或失败。

## M07.03 WSS 连接认证与路由

**目标与边界：** 为在线用户提供及时消息提示，管理短期连接认证、订阅与多实例路由。连接不是持久消息队列，后台断连属于正常情况；本项不替代 .02 保存和 .04 补拉。

**工程结构：** 拟建 `WsTicketService`、`CampusWebSocketHandler`、`ConnectionRegistry`、`UserMessageRouter`。HTTPS 登录态申请单次票据 → WSS 握手／首帧交换 → 原子消费票据 → 绑定 user/authVersion → 订阅授权 → 接受持久化事件推送。采用标准 JSON 消息封装，所有 send 命令委派 .02。

**数据与不变量：** 票据含 jti、user、用途、expiresAt、authVersion，只存摘要或受保护短期状态；认证前连接不可订阅。长期 Token 不放 URL；即使短票据通过握手传输，也要屏蔽 URL／头日志。连接表是可重建缓存，服务端发送前校验当前成员与账户权限，不能用客户端声明的 userId 路由。

**接口契约：** `POST /messages/ws-ticket` 返回 ticket、expiresAt、连接地址；协议帧含 `type,requestId,payload`，推送含 conversationId、seq、messageId。定义 `auth/subscribe/unsubscribe/send/ping` 与对应 ack/error；错误 `WS_TICKET_EXPIRED/WS_TICKET_USED/WS_AUTH_REQUIRED/WS_SUBSCRIPTION_DENIED`，约定关闭码、帧大小和速率限制。

**执行与失败处理：** 消费票据需缓存原子操作，缓存不可用时拒绝新认证并走 HTTP；票据丢失可重新申请。多实例 Redis 广播只唤醒目标实例，丢广播由补拉恢复。撤权事件主动清连接，同时当前权限检查阻止后续发送，不依赖广播准时到达；离线用户不建立无限内存缓冲。心跳与连接上限按真机测量调整。

**依赖与替身：** 依赖 .01/.02、M00、M01；复用 Spring WebSocket 和 uni.connectSocket。A 可用标准 WSS 测试客户端与真实兼容缓存，路由及权限接口用 stub。

**独立验收：** A：同票据并发连接仅一次认证成功；未认证帧、超大帧及非成员订阅被拒绝且无消息泄漏；伪造 payload userId 不改变连接身份。B：两 API 实例间推送可达，停缓存时已持久消息仍能 HTTP 补齐；撤权后下一次分发鉴权拒绝，无新私有推送。C：微信真机测后台返回、网络切换、票据过期与重连，未出现永久连接假设；确认生产 WSS 域名、证书和小程序域名配置实际可用。

## M07.04 历史补拉与已读

**目标与边界：** 从数据库补齐断线消息，让多设备已读一致。此项管理查询、游标、未读计算与变更同步；WSS 送达 ack 不自动等于用户读过，未读不直接用 seq 相减。

**工程结构：** 拟建 `MessageHistoryQueryService`、`ReadCursorService`、`ConversationListQuery` 与游标编解码。客户端携带 afterSeq → 当前成员及历史范围检查 → 按 seq 有界查询 → 返回服务端高水位及 nextCursor；已读命令只推进 `msg_member.read_seq`。删除／撤回需独立变更游标或显式重取窗口，不能只补拉新 seq 而遗漏旧消息状态变化。

**数据与不变量：** read_seq 单调且不超过会话已提交高水位；不会被另一台设备较旧请求倒退。历史返回 tombstone 占位，避免序号缺口误认为丢消息；未读基于需要计数的对方消息过滤。使用 `msg_message_change` 或等效持久 changeSeq 记录旧消息编辑／撤回，公开契约与前端同步确定。

**接口契约：** `GET /conversations/{id}/messages?afterSeq&limit` 返回 items、nextCursor、highWatermark；`GET .../changes?afterChangeSeq` 返回内容状态变更；`PUT .../read {readSeq}` 返回 effectiveReadSeq/unreadCount。错误 `CURSOR_INVALID/READ_CURSOR_OUT_OF_RANGE/CONVERSATION_NOT_ACCESSIBLE`；过旧已清理游标返回 `HISTORY_RESYNC_REQUIRED` 和可访问起点。

**执行与失败处理：** 查询以稳定排序和上限避免无限扫描；已读以条件更新或 greatest 实现单调，事务中写已读事件。客户端先保存消息再推进本地补拉游标；页间新增消息在下一页／轮补齐。统计缓存可重建，过期时回数据库计算，不因此回退 read_seq。历史归档或删除按用户可见保留策略返回明确状态。

**依赖与替身：** 依赖 .01/.02、M00、M01；A 用真实 MySQL 写入固定 seq、本人／对方／墓碑及乱序已读样本。前端同步状态归 M10，不在本项复制本地 store。

**独立验收：** A：断线缺 25 条、每页 10 条，补拉后不漏不重且按 seq 排序；多设备提交 readSeq 20、15、22 后终态 22；提交超高水位被拒绝不清空未读。B：真实消息被撤回后，客户端补拉 changes 更新旧气泡；含本人消息和 tombstone 时未读数按定义一致；非成员历史和 change 接口均拒绝。C：真机在接收后、保存前中断，再进入可补齐；切后台期间消息与撤回同时发生，返回前台后内容、已读及未读角标一致。

## M07.05 业务通知与订阅提醒

**目标与边界：** 把订单、报名、认证等事件转成可靠站内通知，并在用户授权和渠道能力允许时额外提醒。通知失败不得回滚交易；订阅消息是否成功不作为支付、接单或报名成功证据。

**工程结构：** 拟建 `BusinessNotificationConsumer`、`NotificationTemplateRegistry`、`NotificationApplicationService`、`WechatSubscriptionAdapter`。事件消费者 → 按模板解析收件人及最小快照 → 同事务写 notice 和投递任务 → outbox 驱动微信提醒。渠道模板和事件模板分别版本化，点击卡片通过业务引用查询当前资源状态。

**数据与不变量：** `msg_notice` 唯一 `(source_event_id,recipient_id,notice_type)`，保存业务引用、脱敏摘要、模板版本、read_at；`msg_notification_delivery` 保存 channel、授权依据、尝试、渠道状态和稳定业务键。通知正文不放取件码、证件或完整联系方式。用户订阅同意、渠道可发送次数与实际成功投递分别记录。

**接口契约：** `NotificationApi.create(eventId,recipient,businessRef,template,args)` 返回 noticeId；`GET /notices` 有界分页，`markRead` 仅本人。`SubscriptionReminderPort.send(delivery)` 返回 `SENT/NOT_AUTHORIZED/REJECTED/UNKNOWN`，未知结果不可假装失败后无限重发；模板字段缺失为 `NOTIFICATION_TEMPLATE_INVALID`。

**执行与失败处理：** 消费成功标记、站内通知和投递任务同事务，重复事件不重复通知。微信调用事务外执行；未授权保留站内通知并结束该提醒尝试。可重试错误限次退避，结果未知按渠道能力查证；若无幂等／查证能力则限制重发并记录可能重复边界。旧通知卡片不得直接带着旧金额触发业务动作。

**依赖与替身：** 依赖 M00、M01、业务事件契约与微信适配器；可用固定事件和授权 stub 完成 A。M09 维护模板配置，M10 提供真实订阅授权交互；不得默认用户已同意所有提醒。

**独立验收：** A：同订单完成事件重放 10 次只一条 notice 和一项投递任务；无订阅授权时站内通知仍成功、外部调用为零；渠道超时记录 UNKNOWN，业务订单无回滚。B：真实付款、报名和认证事件各对应正确本人通知，跨用户 markRead 拒绝；通知消费者停机恢复后补建且不重记账，旧卡片点击读取最新状态。C：微信真机分别授权／拒绝订阅，核验真实模板投递与跳转；渠道不支持查证的超时场景明确记录限制，不声称提醒绝不重复。
