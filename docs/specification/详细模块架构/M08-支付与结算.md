# M08 支付与结算：详细模块架构

版本：v1.1，2026-09-17。本文是实施与验收设计，未实现或测试。沿用父架构的芋道 pay + WxJava，SDK 负责密码学与渠道协议；仅在固定版本缺失所需接口时评估官方 wechatpay-java 补缺，避免同一业务同时走两套适配器。

## 总览、唯一写入归属与内部依赖

代码根为 `backend/campus-module-finance/`；上游 `yudao-module-pay` 保持最小适配补丁。支付／退款主表优先复用既有模型，P0 冻结字段与状态映射，不另建同义金额事实。业务订单、付款、退款、应付分配、转付是不同聚合；学校运营权限不等于资金操作权限。

| 子模块 | 唯一写入职责 |
|---|---|
| M08.01 | 渠道配置引用、版本与 `fin_recipient_binding` 收款绑定 |
| M08.02 | 上游付款单创建、`fin_business_payment` 业务关联、预支付尝试快照 |
| M08.03 | 通知 inbox、付款可信状态入口与查单恢复；调用共享付款聚合方法更新主表 |
| M08.04 | 上游退款单和金额预占、退款结果处理 |
| M08.05 | `fin_business_fund_guard`、冻结原因明细、`fin_settlement` 与分配明细 |
| M08.06 | `fin_payout` 转付尝试与结果；结算状态仅通过 .05 聚合方法更新 |
| M08.07 | `fin_ledger_txn`、`fin_ledger_entry`、冲正关系与来源唯一约束 |
| M08.08 | 对账批次、账单元数据、`fin_reconcile_case` 差异案件 |

内部提供 `api/internal/FundGuardCoordinator`、`LedgerPostingApi`、付款/退款/结算聚合方法供以上子模块调用。这些是同一单体内的代码责任边界，不能拆成各自提交的网络服务。.05 的 guard 基础方法与 .07 的原子台账 API 先交付契约和最小实现；随后 .01 → .02 → .03/.04，.05 分配规则与 .06 打款联调，.08 汇总核对。实施顺序不按编号机械串行。

统一财务锁次序为：业务 guard → 已存在的结算（按 ID 排序）→ 付款 → 退款 → 转付 → 必要台账汇总行。guard 的业务类型＋业务 ID 唯一；不存在时用唯一约束安全创建后再锁。跨业务命令按业务键排序，首期尽量单业务处理。调用方若需锁履约行，先锁本域订单/负载再进入 Finance；Finance 不反向锁业务表。只有最终有效状态更新时才发台账、outbox，三者在同一事务；.05/.07 使用 REQUIRED 或 MANDATORY 传播，禁止 REQUIRES_NEW。网络请求在提交后发出，未知结果保留预占。

所有子模块 A 级验收使用真实 MySQL/InnoDB，邻域契约 stub；.05 guard 和 .07 ledger 属于核心一致性依赖，资金状态验收须使用其真实最小实现，或明确仅验证接口调用、等待 B 补齐原子性。C 以实际产品权限与受控小额资金为前提，缺权限时记录未验证，不允许宣布真实资金上线。转付对账异常通过公共事件／异常端口上报，由 .08 消费；.06 不直接依赖对账服务实现，.08 可调用独立的转付结果入口，避免彼此服务构造循环。

## M08.01 渠道配置与收款人绑定

**目标与边界：** 管理可用商户、AppID、收款和转付能力、已核准场景及接单者收款身份。接入成功收款不推导出转付或分账权限；不创建充值提现钱包，不由学生提交任意 OpenID 决定收款人。

**工程结构（目录／类／分层）：** `application/channel/ChannelCapabilityService`、`RecipientBindingService`；`domain/channel/MerchantCapability`、`RecipientBinding`；`infrastructure/wechat/WxJavaConfigProvider`、`SecretProvider`；管理 controller 仅暴露脱敏配置与检测结果。私钥、APIv3 密钥在密钥系统或服务环境注入，数据库只存引用、序列号和版本。

**数据与不变量：** 配置唯一键覆盖商户与应用组合，独立 payment/refund/payout 能力及生效时间；关闭新增收款不能阻断历史退款。收款绑定包含内部 memberId、appid、openid、验证来源、bindingVersion、状态；绑定通过 M01 的已验证会话建立。转付保存绑定快照，绑定变更不能修改已提交单据；未执行的旧绑定如何重新审核由明确命令控制。

**接口契约（输入输出错误）：** `ChannelApi.requireCapability(merchantRef,scene)` 返回配置版本和适配器标识，不返回私钥；`RecipientApi.resolveForPayout(memberId,merchantRef)` 返回服务端绑定快照；绑定入口接收一次性身份验证凭据。错误含 `CAPABILITY_NOT_APPROVED`、`APP_MERCHANT_MISMATCH`、`RECIPIENT_UNBOUND`、`BINDING_REVOKED`，不得以用户可写字段覆盖身份。

**执行与失败处理（事务与外部边界）：** 渠道参数验证在事务外完成，结果按版本落库；启用操作重新验证当前配置版本并审计。SDK 初始化失败关闭新增请求并告警，历史任务保留原配置引用可恢复。需要用户确认收款时由 .06 返回对应参数；前端确认页面 success 只说明界面动作，最终结果需渠道通知或查询。

**依赖与替身：** M01 微信身份、M00 配置/密钥/审计、上游 pay/WxJava。A 使用假 SecretProvider 和身份 stub，不使用真实密钥。B 验证真实授权范围与 SDK 适配器；C 验证获批商户、小程序与转付场景，不能仅凭字段填全开放收费。

**独立验收：** A：① 只有收款权限时请求 payout，断言拒绝且网关零调用；② U1 提交 U2 OpenID，断言绑定仍以服务端身份为准或拒绝；③ 切换绑定后读取既有转付，断言 recipient 快照不变、配置审计一条。B：身份注销或停用后新转付被拦，历史退款仍能查询；秘密字段不出现在日志/DTO。C：真机核验实际 AppID、商户与用户确认流程，留脱敏成功/拒绝证据。

## M08.02 支付单与预支付

**目标与边界：** 把可信业务应收转换为唯一付款关联，再通过既定商户单号获取预支付参数。HTTP 重试、客户端刷新和预支付参数过期不得产生第二个可扣款事实；不负责判定跑腿履约完成。

**工程结构（目录／类／分层）：** `application/payment/CreatePaymentService`、`PrepayService`；`domain/payment/BusinessPayment`、`PaymentAttempt`；`infrastructure/payment/UpstreamPayAdapter` 与 WxJava 网关。共享聚合模型由本项维护，.03 通过 applyVerifiedResult 方法更新渠道结果，避免两个字段体系。

**数据与不变量：** `fin_business_payment` 按业务类型、业务 ID、付款目的唯一；金额、payer、币种、school、merchantRef 是服务端批准快照。渠道尝试保存 outTradeNo、配置版本、请求摘要和过期时间；同商户单号唯一。更换尝试必须先确认旧单关闭且未支付，首期采用单订单固定渠道，不支持并行切换渠道扣款。

**接口契约（输入输出错误）：** 内部 `FinanceApi.createPayment(businessType,businessId,payer,amountFen,currency,priceVersion)` 返回 paymentId，拒绝来自公网的裸资金命令；`POST .../payments/{id}/prepay` 校验本人和有效状态，返回 ready+调起参数或 processing+查询入口。错误含 `PAYMENT_AMOUNT_CONFLICT`、`PAYMENT_ALREADY_SUCCEEDED`、`CAPABILITY_DISABLED`、`PAYMENT_CLOSED`、`IDEMPOTENCY_CONFLICT`。

**执行与失败处理（事务与外部边界）：** createPayment 加入业务创建事务，仅建 guard/关联/本地付款记录，不调用渠道。预支付先在短事务分配稳定单号与调用意图，提交后发 SDK 请求，再用版本检查持久化参数。崩溃后先查原单并以原参数恢复；预支付有效期到达不等同付款单关闭。用户关闭页面不取消后台事实，关单也必须核实渠道结果。

**依赖与替身：** .01 配置，.05 guard，.03 查询结果契约，M00 幂等/outbox，上游 pay。A 网关 stub 支持正常、超时已创建、参数不符和重复；真实数据库保证业务关联唯一。依赖 .03 接口不要求主动查询线程在同一测试运行。

**独立验收：** A：① 同用户两次并发 prepay，断言一个 outTradeNo 与相同摘要，允许重复网络发送但逻辑渠道单仅一笔；② 渠道已创建后本地断线，恢复仍查同号，数据库无新尝试；③ 同业务再次请求不同金额，断言冲突且原金额不变。B：M05 创建事务回滚时关联、guard、付款均回滚且渠道调用零；参数过期重取不重复扣款。C：真机拉起支付、取消与再次进入共用原单，后端查明状态，小额单据与渠道侧一致。

## M08.03 回调查单与可信结果

**目标与边界：** 汇合支付通知和主动查单，形成唯一可信付款事实，保证无通知、重复或乱序时仍可恢复。回调入口不套用户登录，但必须通过渠道身份验证；来自客户端的“已付款”只请求查询。

**工程结构（目录／类／分层）：** `controller/callback/WechatPaymentCallbackController` 保留原始 body；`application/payment/PaymentResultService`、`PaymentQueryJob`；`infrastructure/wechat/VerifiedNotificationParser` 使用 WxJava 验签解密；`infrastructure/inbox/PaymentInboxRepository` 负责可靠接收。共享 `VerifiedPaymentResult` DTO 不暴露 SDK 对象。

**数据与不变量：** inbox 唯一键为渠道、商户、通知 ID，并保存报文摘要与脱敏解析结果；加密原报文按限定保留期保护。付款结果检查 outTradeNo、transactionId、mchid、appid、金额、币种和业务关联。渠道流水在匹配范围唯一，同成功只能一次入账；未知枚举归入待核对，不回退已成功状态。

**接口契约（输入输出错误）：** `acceptNotification(rawBody,headers)` 返回渠道应答；`applyVerifiedResult(paymentId,result,source)` 返回 applied/duplicate/conflict。验证失败拒绝，数据库不可用返回可重试非成功应答；已验真但不匹配记录异常并隔离，不推进业务。`queryPayment` 返回本地与最近渠道核对时间，不把网络失败编码成付款失败。

**执行与失败处理（事务与外部边界）：** 验签与 SDK 解析先于写入；可靠 inbox 提交后才能成功应答，若同步处理则 inbox、付款状态、.07 台账、outbox 同事务。异步模式消费者标记与后三项同事务，ACK 后崩溃可扫描恢复。查单网络调用在事务外，结果走相同应用入口和锁序；租约只是调度机制，不绕过业务唯一约束。付款成功后由 M05 消费事件决定开放或退款补偿。

**依赖与替身：** .01 配置，.02 付款聚合，.05 guard，.07 ledger，M00 inbox/outbox；A 使用固定合法/非法报文及可控查单 stub，必须实际执行验签契约测试，禁止只 mock 验签返回 true。B 连真实 M05 事件处理器。

**独立验收：** A：① 同成功通知并发重放并同时查单，断言一次成功转移、一次台账来源、一次成功事件；② 修改原始 body 或金额/AppID，断言不推进、不入账；③ inbox 已持久化后杀进程，重启扫描可处理，处理事务中失败则状态/台账/事件全回滚。B：已关闭跑腿订单收到成功只生成稳定退款补偿；消费者断线不会重复开放。C：真实通知签名及公钥/证书配置有效，主动查单覆盖关闭客户端情况，渠道与数据库流水可核对。

## M08.04 退款预占与退款执行

**目标与边界：** 对经业务与财务权限批准的退款建立不可超额的申请，执行原路退款并追踪终态。申请受理只代表请求成立；不以退款关闭履约订单，不自动扣回已转付报酬。

**工程结构（目录／类／分层）：** `application/refund/RequestRefundService`、`RefundExecuteJob`、`RefundResultService`；`domain/refund/RefundAllocation`、`RefundStatePolicy`；`infrastructure/refund/UpstreamRefundAdapter`。资金命令从内部 API 或具备复核信息的财务管理入口进入。

**数据与不变量：** 复用上游退款主表，扩展业务退款决定 ID、原付款、预占金额、稳定 outRefundNo、请求摘要及渠道终态。成功退款总额＋在途预占总额不得超过实付；同决定只能一笔有效退款。失败必须区分明确终态失败与结果未知，后者不释放预占。部分退款需明确归属分配项，不能只减少总额却仍按原报酬结算。

**接口契约（输入输出错误）：** `FinanceApi.requestRefund(paymentId,decisionId,amountFen,reason,allocationAdjustment)` 返回 refundId、状态与冻结影响。输入来自服务端裁决；前端金额不是批准凭证。错误含 `REFUND_EXCEEDS_AVAILABLE`、`PAYMENT_NOT_SUCCEEDED`、`PAYOUT_CONFLICT_REVIEW_REQUIRED`、`DECISION_AMOUNT_CONFLICT`。查询返回 processing/succeeded/failed/abnormal/unknown 及允许的下一步。

**执行与失败处理（事务与外部边界）：** 按 guard→settlement→payment→refund 锁序预占退款和调整/冻结相应应付，创建 outbox 同事务。外部请求提交后执行，超时保留原退款号查单；只有渠道确认结果时才在同一事务释放/兑现预占、调整 .05 分配、写 .07 台账和事件。退款异常进案件，已转付部分需批准垫付或追偿记录。退款与打款只在同 guard 下决定，不依赖延迟事件互斥。

**依赖与替身：** .01 网关配置、.02/.03 可信付款、.05 资金控制、.07 记账、M09 决定权限；A 使用可控退款结果适配器，真实 MySQL 验证超额保护，B 连真实裁决与转付。

**独立验收：** A：① 实付 1000 分并发申请 700/600 分，断言最多一笔预占成功且总额不超 1000；② 同决定换幂等键重试，仍仅一个 outRefundNo；③ SDK 受理后断网，预占不释放，查询成功后只退款记账一次。B：退款与打款竞争时分配与在途资金一致；退款成功后按剩余有效分配结算，已打款退款形成垫付记录。C：实际小额全退/部分退、回调与账单一致；异常场景缺真实条件可由受控适配器 B 验证并明确限制。

## M08.05 业务资金控制与结算分配

**目标与边界：** 提供整个资金模块共享的立即生效控制记录，维护冻结原因和应付分配。此处是代码子模块，绝不能以异步微服务代替其同事务 API。结算生成只代表业务报酬成立，尚需等待、审核、绑定和渠道能力满足才可执行转付。

**工程结构（目录／类／分层）：** `api/internal/FundGuardCoordinator`；`application/settlement/SettlementService`；`domain/settlement/BusinessFundGuard`、`SettlementAllocation`、`FreezeReason`；`infrastructure/settlement/GuardMapper/SettlementMapper`。guard 基础实现先于所有有资金副作用的子模块交付，ledger API 与其共同纳入事务骨架。

**数据与不变量：** guard 按 businessType/businessId 唯一，原因明细按业务＋reasonType＋reasonId 唯一。结算按业务＋分配版本唯一，分配项按有效受益人及用途唯一；保存原计价、完成依据、受益 memberId、净应付与平台金额，转付不能替换受益人。多个争议/退款/对账原因全部解除前仍冻结。无结算时先建 guard，后续结算继承冻结；退款影响按 .04 的分配调整命令落定。

**接口契约（输入输出错误）：** `prepareSettlement(businessRef,completionId,priceSnapshot,beneficiary)`、`freezeSettlement(businessRef,reasonRef)`、`releaseFreeze(reasonRef,approvedDecision)`、`reservePayout(allocationId,expectedVersion)`。返回可结算金额、冻结原因、是否已有执行中转付；错误为 `SETTLEMENT_CONFLICT`、`FUNDS_FROZEN`、`NOT_DUE`、`ALLOCATION_INCONSISTENT`。普通学生和校级运营不能直接指定分配金额。

**执行与失败处理（事务与外部边界）：** 所有方法加入当前数据库事务，guard 先锁；争议受理、业务案件关联与冻结必须一起提交，不能 REQUIRES_NEW。结算分配和应付台账同事务；打款预占检查全部冻结、有效付款与剩余应付后进入执行中。审核通过只解除该审核原因。已进入执行的转付与冻结并发时，如实返回资金在途，不伪造撤回；禁止在持锁事务内调用微信。

**依赖与替身：** M00 事务、.07 LedgerPostingApi、.03 付款事实、.01 收款身份验证；调用方 M05/M09 使用版本化命令。A 使用真实 guard/ledger 和邻域 stub；B 必须真实 M05、M09 同事务联调。

**独立验收：** A：① 先冻结再创建结算，断言生成即冻结、网关零调用；② 两个独立原因只解一项，仍不可 reservePayout；③ 同 completionId 重放只产生一次分配和应付台账，金额不同报冲突。B：停掉消费者后受理争议，guard 立即生效；受理事务失败案件与冻结一起回滚；屏障竞争冻结/打款只出现先冻结拒绝或先执行告知在途。C：获批资金环境核对最终付款受益人、分配与实际到账；仅 A 通过不能开放真实跑腿。

## M08.06 跑腿员打款与未知态恢复

**目标与边界：** 将已批准、未冻结的净应付发送给绑定跑腿员，并在超时、用户未确认、重复通知时恢复准确状态。客户端收款页成功回调不计为到账；不实现任意金额提现，不把同一应付多次生成新的有效付款。

**工程结构（目录／类／分层）：** `application/payout/PayoutService`、`PayoutExecuteJob`、`PayoutRecoveryJob`；`domain/payout/PayoutAttempt`、`PayoutStatePolicy`；`infrastructure/wechat/WxPayoutGateway`。用户确认参数通过本人授权接口短期返回，不在普通订单日志、消息广播中发送完整 package。

**数据与不变量：** `fin_payout` 保存 allocationId、attemptNo、outBillNo、immutableRequestDigest、recipientBindingVersion、商户/AppID/OpenID 快照、金额、原始渠道状态与 leaseVersion。一个分配最多一笔有效在途转付，累计成功和在途不得超净应付。终态失败后获准重试才能产生新的 attempt；未知态保持原号和预占。绑定变化不会改变旧请求摘要。

**接口契约（输入输出错误）：** `PayoutApi.request(allocationId,approvalRef)` 返回 payoutId/状态；`query` 返回 lastCheckedAt；`getConfirmationPackage` 仅本人且仍待确认时返回匹配参数；`cancelIfSupported` 返回撤销申请状态。错误含 `PAYOUT_FROZEN`、`RECIPIENT_INVALID`、`PAYOUT_ALREADY_IN_FLIGHT`、`CHANNEL_PERMISSION_MISSING`、`RESULT_UNKNOWN`。

**执行与失败处理（事务与外部边界）：** guard 下 .05 预占与本单创建/outbox 同事务，提交后调用渠道。网络超时、未知错误先查原单，禁止自动换号；查询超出渠道窗口则移交资金账单与 .08 人工核对，仍不释放。受理后冻结可尝试渠道支持的撤销，但结果经查单/通知确认。终态变更、分配兑现或释放、.07 台账和 outbox 原子提交。旧 worker 不得凭过期租约覆盖新结果，所有返回走状态聚合校验。

**依赖与替身：** .01 实际能力与绑定、.05 分配、.07 台账、.08 对账，M00 任务与审计。A 渠道替身必须能模拟“扣款已成功但 HTTP 超时”、待确认、撤销未完成与乱序；不是只返回 success 的 mock。

**独立验收：** A：① 扣款后超时并重启 worker，断言所有重试/查单沿用 outBillNo，逻辑转账一次；② 待确认时重复申请与解绑，原单收款快照不变、不建新单；③ success 后收到旧 processing，状态和台账不回退。B：冻结/退款与请求并发净应付不超分配；台账写失败回滚本地成功状态，重复渠道事实可恢复。C：获批小额实际到账、待用户确认和查询一致，确认页面关闭不伪造失败，到账证据与原结算逐笔相符。

## M08.07 追加台账与冲正

**目标与边界：** 记录业务资金事件的可追溯、借贷平衡台账，为收入与差异核对提供事实。它是平台内部业务台账，不是学生可消费余额，也不自动替代正式会计账。账户科目和报表口径在实施前与实际经营流程冻结。

**工程结构（目录／类／分层）：** `api/internal/LedgerPostingApi`；`application/ledger/LedgerService`；`domain/ledger/PostingRule`、`JournalEntry`、`AccountRef`；`infrastructure/ledger/LedgerMapper`。源事件到分录使用有版本的确定性规则，controller 不接受任意分录；更正从受权财务命令与审批进入。

**数据与不变量：** `fin_ledger_txn` 对 sourceType/sourceId/effectType 唯一，保存规则版本和摘要；`fin_ledger_entry` 按事务与行号唯一、金额为整数分，同币种借贷相等。渠道实付、退款、费用、跑腿应付、实际转付、垫付/追偿分别标识；预占和实际资金流严格区分。已提交分录不可原地修改或删除，冲正关联原 txn 并有独立批准来源。

**接口契约（输入输出错误）：** `post(sourceRef,effectType,postingFacts)` 返回 txnId/duplicate；`reverse(originalTxnId,correctionDecisionId,reason)` 返回冲正 ID。相同来源不同金额报 `LEDGER_SOURCE_CONFLICT`；不平衡、币种混用、越权科目、重复超额冲正分别拒绝。查询接口输出账户或业务维度汇总，权限和学校范围来自后台身份。

**执行与失败处理（事务与外部边界）：** post 必须在调用方事务中执行；付款/退款/分配/转付终态与分录和 outbox 一起提交。不能先成功写状态、再异步补“必须有”的资金分录。唯一键冲突核对摘要，一致返回原 txn，不能吞掉不同金额。批量对账修复逐笔调用源业务命令与 post，禁止直接填平汇总差额。汇总表可重建，非金额权威来源。

**依赖与替身：** M00 数据库/审计/事务，账户字典和 PostingRule；A 可独立用真实 MySQL 测试，不依赖微信。与 .03–.06 的状态提交关系必须 B 联调；真实渠道验证通过 .08 对账体现。

**独立验收：** A：① 同来源并发 post 100 次，断言一条 txn、固定分录数与借贷零差；② 在第二行插入注入故障，断言整笔分录及调用方测试状态均回滚；③ 改金额重放同来源被拒绝，原分录不变；冲正两次同决定返回同冲正。B：模拟付款成功写台账失败，付款状态/outbox 无提交，重试后全部成立一次；已转付退款形成真实垫付而非虚构收回。C：抽取小额收付退款渠道流水核对台账来源，平台收入不得等于全部交易额。

## M08.08 渠道对账与差异处理

**目标与边界：** 用渠道交易及资金账单验证收款、退款、费用和转付，发现通知遗漏、金额不符、未知转付和恢复备份后的资金缺口。对账发现问题不代表可以自动重付；不通过人工直接改成功金额来“平账”。

**工程结构（目录／类／分层）：** `application/reconcile/BillImportJob`、`ReconcileService`、`ResolveDifferenceService`；`domain/reconcile/BillRow`、`DifferencePolicy`；`infrastructure/bill/WechatBillAdapter`、私有归档与流式解析器。差异看板由 M11 集成，案件审批调用财务受控 API。

**数据与不变量：** 账单批次按渠道/商户/类型/账期/文件摘要识别，记录下载时间、原始摘要、解析版本和状态；行按渠道流水及条目类型去重。`fin_reconcile_case` 保存两侧快照、差异类型、责任人、处理理由和证据。账单元金额转整数分用十进制定点解析，不走浮点数。文件归档、付款/退款/费用/转付口径分别核对。

**接口契约（输入输出错误）：** `reconcile(merchantRef,billType,billDate)` 返回 batchId 与进度；`resolve(caseId,expectedVersion,decision,evidenceRef)` 返回处理状态。错误含 `BILL_NOT_READY`、`HASH_MISMATCH`、`BILL_SCHEMA_UNSUPPORTED`、`DIFFERENCE_REVIEW_REQUIRED`。人工动作只能重查、补应用可信渠道事实、批准冲正或业务异常处理，不提供“标成功并忽略渠道”按钮。

**执行与失败处理（事务与外部边界）：** 下载在事务外且遵守地址有效期，校验摘要后归档并分批解析；每批处理与检查点同事务，可重跑。逐笔匹配后通过 .03/.04/.06 同一结果入口补齐遗漏，调用 .07 保证不重复账务。缺失来源映射或金额冲突隔离人工确认；不能凭商户付款记录自行猜测受益人。恢复旧备份时暂停新资金动作，补齐丢失窗口与稳定单号，核对未决项后才恢复执行。

**依赖与替身：** .01 商户配置、.03/.04/.06 查单和可信应用、.07 台账，M00 文件/任务/审计；A 使用官方格式脱敏账单 fixture 与渠道 stub、真实 MySQL。B 联调故障恢复和重复应用，C 使用实际商户账单并区分交易账单和资金账单。

**独立验收：** A：① 同账单重复导入、半途崩溃后重跑，断言行与案件不重复、检查点继续；② 改一个文件字节或非法元金额，摘要/解析失败且无账务变化；③ 渠道成功本地缺失、金额不符、转付未知分别生成指定差异。B：补应用缺失成功只能增加一次台账；冲突不自动打款；旧备份恢复后先渠道重建/核对而非重发历史付款。C：获取真实交易与资金账单，逐项核实小额支付/退款/费用/转付和最终余额，留脱敏报告与未决差异清单。
